## WI-1 — Password reset flow (Pulse: 3bd3309b-308c-4bbf-a562-000f715a6ea6, 32066456-79b0-487e-8792-4897dd485df6)
Real bug confirmed: `client/src/pages/ResetPasswordPage.tsx:61` calls `supabase.auth.updateUser()`
immediately on submit with no guard that the Supabase Auth v2 recovery session (established
async from the URL token via `onAuthStateChange` `PASSWORD_RECOVERY`) has actually landed yet.

- AC-01: Given a user clicks a valid password-reset email link, when the page loads, then the
  app waits for the `PASSWORD_RECOVERY` auth event (or an established session) before enabling
  the new-password form.
- AC-02: Given the recovery session is not yet established, then the submit control is disabled
  with a "Verifying reset link…" loading state, not silently submittable.
- AC-03: Given the recovery session is established, when the user submits a new password, then
  `updateUser` succeeds and the user is redirected with a success message.
- AC-04: Given `updateUser` errors (weak password, network), then a clear human-readable error
  is shown (already true today — not swallowed).
- AC-05: Given the link is invalid/expired and no recovery event ever fires, then a clear error
  state is shown after a bounded wait, not an infinite spinner.
