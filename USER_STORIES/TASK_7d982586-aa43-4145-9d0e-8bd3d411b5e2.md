# Phase 1: landlord uploads a lease and tenant signs it in-app via existing DocuSign

Task id: `7d982586-aa43-4145-9d0e-8bd3d411b5e2`

## Source

Customer request (phase 1 only): a landlord uploads their own lease PDF for a specific tenant and property, the tenant signs it inside the app with the existing DocuSign embedded signing (account already configured as `DOCUSIGN_ACCOUNT_ID`, the account the customer identified as 3030222 — do not hardcode a second account), the signed PDF is stored and visible to both parties, and the landlord can see status sent / viewed / signed (plus declined and voided). A copy is kept and sent the same way the existing landlord agreements keep an executed PDF. Out of scope: state lease templates and a lease generator.

## Schema checked before these ACs

Live `information_schema` (public) on this run:

- `properties.landlord_id` uuid NOT NULL, `properties.title` text, `properties.address_line1` text, `properties.city` text, `properties.lease_term` text (duration string — not used for this feature)
- `applications.id`, `applications.tenant_id`, `applications.property_id` — no envelope or document columns
- `profiles.id`, `profiles.display_name`, `profiles.docusign_envelope_id`, `profiles.docusign_envelope_status`, `profiles.plaid_agreement_envelope_id` — landlord-agreement columns, not per-tenant leases
- `message_threads.landlord_id`, `message_threads.tenant_id`
- `tenant_invite_restrictions.tenant_id`, `tenant_invite_restrictions.landlord_id`, `tenant_invite_restrictions.ends_at`
- No `public.leases` table yet. Phase 1 adds it (additive). Storage bucket `leases` is new and private.

## Acceptance criteria

AC-01: Given a PDF buffer, when a lease envelope definition is built, then document 1 is that PDF (`fileExtension` pdf, `transformPdfFields` false), the signer `clientUserId` is the tenant id, `requireIdLookup` is false, and there is no second document and no radio group.
Verified by: test `lease envelope uses the uploaded PDF as document 1`

AC-02: Given a multi-page PDF, when signature tabs are placed, then a required SignHere and a required DateSigned sit on the last page inside the page bounds, with no anchor strings and no field-placement editor.
Verified by: test `lease signature tabs sit on the last page`

AC-03: Given a property label, when the envelope email subject is built, then it identifies a Rental City lease for that property and strips line breaks.
Verified by: test `lease email subject names the property`

AC-04: Given landlord/tenant/property signals, when send authorization is decided, then the send is allowed only when the caller owns the property and the tenant is connected by an application on that property, a message thread, or an active invite. A completed lease is never voided; an in-progress lease is voided before another is created.
Verified by: test `lease send authorization and void rules`

AC-05: Given a lease row, when a public view or download decision is made, then storage paths are omitted and only that lease's landlord or tenant may download.
Verified by: test `lease view hides storage paths and limits download`

AC-06: Given DocuSign envelope status, when completion is decided, then the signed PDF is stored only for `completed`, other DocuSign statuses are persisted for the landlord (sent, delivered as viewed, declined, voided), and the usage log line contains lease id, envelope id, and timestamp without calling DocuSign.
Verified by: test `lease completion decision and usage log do not create an envelope`

AC-07: Given the embedded return URL, when a lease ceremony finishes, then the URL includes `type=lease` and the envelope id, and the return page still accepts `equifax` and `plaid`.
Verified by: test `lease return URL is type=lease` and file:line `client/src/pages/DocusignReturnPage.tsx`

AC-08: Given an envelope built without the lease flag, when the definition is built, then document 1 does not set `transformPdfFields`, so Equifax and Plaid envelopes stay on the existing path.
Verified by: test `non-lease envelopes do not force transformPdfFields`

AC-09: Given the landlord tenant profile for a property that landlord owns, when there is no lease, then the page shows Not sent, a PDF-only upload, and one send action. No property in context means no upload control. Status labels cover Not sent, Sent, Viewed, Signed, Declined, and Voided, with download for the original and, after signing, the signed copy.
Verified by: test `lease status labels match the landlord view` and file:line `client/src/components/LandlordLeaseCard.tsx`

AC-10: Given a tenant with a sent or delivered lease, when they use the app shell, then a prompt opens the embedded signing iframe and the return posts `source: docusign-return` for `type=lease`. The signed copy stays available to that tenant.
Verified by: file:line `client/src/components/TenantLeasePrompt.tsx` and file:line `client/src/pages/DocusignReturnPage.tsx`

AC-11: Given a non-PDF, empty, or oversized file, when it is checked, then it is rejected before any envelope is created. Phase 1 has no lease generator and no state template.
Verified by: test `lease upload rejects empty, non-pdf, and oversized files`

AC-12: Given the new `public.leases` table and private `leases` bucket, when the migration is applied, then the table has landlord_id, tenant_id, property_id, nullable application_id, original_storage_path, nullable signed_storage_path, nullable envelope_id, envelope_status, sent_at, completed_at, created_at, and updated_at, with one open row per landlord+tenant+property, and RLS so the Data API cannot read another tenant's lease.
Verified by: file:line `supabase/migrations/20261103163000_leases.sql` and a follow-up `information_schema` read after apply
